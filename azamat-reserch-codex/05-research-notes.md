# Небольшое исследование: статистика, экономика и LLM

Дата проверки: 23.09.2026. Ниже — проверенные сведения из официальной документации NVIDIA и OpenAI и отдельно наши проектные выводы. Наличие ключей, кредитов, конкретных моделей и доступа у команды не проверялось; платные API-вызовы не выполнялись.

## Проверка идеи по коду и математике

**Единица исследования выбрана правильно:** исходный тариф × ARPU-сегмент → целевой тариф. Публичный скоринг связывает эффект именно с этими полями; data/call меняют состав аудитории, но не коэффициент внутри ячейки. Из этого следует экономия пилотов на излишнем дроблении. [scoring_core.py](<../amir-research/scoring_core.py#L145>).

**Вес пилота равен обратной дисперсии его среднего.** Шум одного клиента равен 0.804, ошибка среднего — `SE=0.804/√n`. Точность наблюдения — `1/SE²=n/0.804²`; дополнительное умножение на n неверно. При n=150 оно завысило бы вес в 150 раз. Обе сравниваемые файловые версии используют правильное обновление; ошибка встречалась в более раннем сообщении, не в текущем документе Claude. [Среда кейса](<../amir-research/environment.py#L49>), [Auburn University, слайды 46–48](https://webhome.auburn.edu/~ezc0066/CourseMaterials/STAT7630_Bayesian/STAT7630-Slides/S7630_S5_ConjugateFam.pdf), [NIST об ошибке среднего](https://www.itl.nist.gov/div898/handbook/eda/section3/eda352.htm).

**Положительный процент не равен прибыли.** Из публикуемой формулы выводим условие: `(mean−k×posterior_sd)×сумма ARPU−цена контактов > 0`. Даже оно не гарантирует положительный результат всей стратегии: плохие пилоты уже исполнены, оценки шумные, лучший из многих вариантов может оказаться случайным лидером. [Расчёт net и дедупликация](<../amir-research/scoring_core.py#L241>).

**Экономика каналов не сводится к HIGH→ads.** Наш расчёт из открытых множителей: если g — SMS gross на клиента, то SMS выгоднее push лишь при g>17.33, ads выгоднее SMS при g>58.5, до учёта дефицита денег. При g=10 push даёт 7.69, SMS — 6 у.е. Остаток 40 000 после 15 000 SMS позволяет теоретически 2 222 замены канала на ads по дополнительным 18 у.е.; допустимые фильтры могут не позволить именно такой размер. [Каналы и отсечение](<../amir-research/scoring_core.py#L195>).

**Итог:** сохраняем приоритет ценных ячеек, разнообразие гипотез, сравнение push/SMS/ads, слабый prior, адаптивную остановку и воспроизводимость. Это аргументированный выбор MVP на 5 часов, а не доказательство превосходства над всеми алгоритмами; сравнительные запуски готового агента ещё предстоят.

## Что подтверждается источниками

**NVIDIA действительно допускает использование библиотеки `openai`.** В официальном примере NVIDIA API Catalog клиент `OpenAI` направлен на `https://integrate.api.nvidia.com/v1` и использует NVIDIA API key. Это позволяет сделать небольшой адаптер провайдера, не поднимая свой inference-сервер. Пример подтверждает совместимость конкретного API-вызова, а не универсальную поддержку всех параметров OpenAI каждым NIM endpoint. [Официальный пример NVIDIA](https://build.nvidia.com/openai/gpt-oss-120b/deploy).

**Ключ NVIDIA и ключ OpenAI — разные учётные данные.** В документации NVIDIA провайдеры имеют отдельные адреса и переменные `NVIDIA_API_KEY` и `OPENAI_API_KEY`. NVIDIA отдельно предупреждает: OpenAI-клиент без явно переданного ключа читает `OPENAI_API_KEY`; при работе с NVIDIA нужно явно передавать соответствующий ключ. Следовательно, одного изменения `base_url` недостаточно. [Конфигурация провайдеров](https://docs.nvidia.com/nemo/datadesigner/v0.7.0/concepts/models/default-model-settings), [настройка клиента NVIDIA](https://docs.nvidia.com/nemo/curator/v26.02/curate-text/synthetic/llm-client).

**Наличие строки с ключом не гарантирует успешный запрос.** Официальная документация OpenAI разделяет временные ограничения, перегрузку и ошибки квоты или биллинга; последние повторными попытками не исправляются. Наш вывод: нельзя обещать работающую LLM на судействе только потому, что там зададут переменную окружения. Доступную модель, провайдера и бюджет нужно проверить заранее в предусмотренном организаторами порядке. [OpenAI: ограничения и обработка ошибок](https://developers.openai.com/api/docs/guides/rate-limits).

**Повторяемый LLM-ответ не является гарантией API.** Для `seed` в Chat Completions OpenAI прямо описывает только best effort и отсутствие гарантии детерминизма. Поэтому фиксированные prompt, seed и температура сами по себе не доказывают идентичность `submission.csv`. Кроме того, поддержка параметров зависит от модели. [OpenAI: Chat Completions](https://developers.openai.com/api/reference/python/resources/chat/subresources/completions/methods/create).

**Одного `try/except` недостаточно для ограничения времени.** OpenAI документирует стандартный timeout SDK в 10 минут и автоматические повторные попытки. В документации rate limits отдельно указано, что timeout попытки не обязательно ограничивает всю операцию. Нужно явно ограничивать время и число повторов; значения по умолчанию не подходят для короткого хакатонного запуска. [OpenAI: timeouts](https://developers.openai.com/api/docs/guides/flex-processing), [OpenAI: retries](https://developers.openai.com/api/docs/guides/rate-limits).

## Как применить за пять часов

Рекомендация команды: сначала детерминированное Python-ядро формирует пилоты, обновляет оценки, выбирает кампании и сохраняет результат. После этого необязательный LLM-модуль объясняет уже рассчитанный план аналитику: почему выбраны сегменты, где неопределённость и как распределён бюджет. В запрос достаточно передавать компактную агрегированную таблицу, без строк абонентов.

LLM включается явным режимом `--explain`, а не автоматически при обнаружении ключа. Конфигурация содержит провайдера, endpoint и доступную модель; секрет передаётся только через переменную окружения. Один короткий запрос с небольшим лимитом ответа, явным timeout около 15 секунд и отключёнными автоматическими повторами — разумный стартовый режим для демонстрации. При любой ошибке выводится локальный шаблон отчёта. Сам CSV от наличия ключа и исхода запроса не меняется.

Автоматически принимать LLM-совет о новом канале или ранжировании в оценочном запуске мы не рекомендуем: результат начнёт зависеть от сети и ответа модели. Совет можно показать рядом с планом как материал для аналитика. Такая архитектура снижает нагрузку: один агрегированный запрос на запуск вместо обработки каждого клиента. Это инженерный вывод, а не обещание баллов: зачёт LLM-компонента зависит от критериев организаторов.
