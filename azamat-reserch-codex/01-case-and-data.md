# Кейс, ограничения и фактические данные

## Источники и границы выводов

Основа: переданный PDF (исходный материал предоставлен отдельно), [PARTICIPANT_GUIDE.md](<../amir-research/PARTICIPANT_GUIDE.md>), вставленный текст с критериями оценки (исходный материал предоставлен отдельно), CSV и публичный код из [пакета участника](<../amir-research>).

Числа ниже получены чтением CSV: строки считаются без заголовков, уникальность и пересечения — по идентификаторам абонентов. Отдельные клиентские ID в отчёт не включены. Входные файлы не изменялись. Все данные синтетические: выводы описывают условия хакатона, а не реальный бизнес Beeline.

Правила задания отделены от проектных предложений: лимиты ниже взяты из материалов; размеры списков гипотез, резерв разведки и цели быстродействия в остальных документах — наши стартовые решения для проверки.

Актуальный срок разработки по уточнению команды — **5 часов**. Он заменяет первоначальный девятичасовой график, но не меняет ограничения времени исполнения агента в ТЗ.

## Что требуется сдать

| Требование организаторов | Как учесть |
|---|---|
| `agent.py`, класс `Agent`, метод `act(env)` | Единая точка входа агента |
| От 1 до 10 корректных финальных кампаний | Валидировать тариф, канал, фильтры, непустую аудиторию |
| Использование пилотов и их результатов | Менять оценки и решения после `env.run_pilot` |
| `submission.csv` | Генерировать штатным `python make_submission.py` |
| `requirements.txt`, если нужны библиотеки | Зафиксировать проверенные версии зависимостей |
| До 10 минут на работу агента | Внутренний дедлайн до 4 минут; цель существенно быстрее |

Число **10** относится к финальному списку. Пилоты добавляются к нему при оценке и тоже влияют на результат. Основная метрика — `net_arpu_gain`, то есть прирост относительно базы минус стоимость контактов. Общую базовую выручку нельзя выдавать за заработок агента.

| Общий ресурс | Лимит |
|---|---:|
| Маркетинговый бюджет | 100 000 у.е. |
| Все контакты, включая пилотные и повторные | 15 000 |
| Аудитория одной финальной кампании | До 5 000 |
| Число пилотов | До 20 |
| Запрошенная аудитория одного пилота | 10–200 |

| Канал | Цена контакта | Множитель в публичном скоринге |
|---|---:|---:|
| push | 0 | 0.50 |
| sms | 4 | 0.65 |
| digital_ads | 22 | 0.85 |
| call | 160 | 1.20 |

Значения каналов — из [публичного scoring_core.py](<../amir-research/scoring_core.py#L16>). Множитель действует на вероятность отклика, которая ограничивается единицей; это не гарантированная конверсия канала.

Сумма `predicted_arpu` равна **150 641 084,2463 у.е.**, что соответствует округлённой базе в кейсе. Это готовый вес экономического результата; строить ещё один прогноз ARPU в MVP не требуется.

## Подготовка данных: только необходимое

| Найденная проблема | Действие участника 1 |
|---|---|
| 6 точных дубликатов смен | Удалить в локальной таблице для исторических агрегатов |
| 1 406 строк истории с нулевым ARPU до смены и одна с отрицательным | Не делить на этот ARPU; считать отдельно или исключить из оценки процентов; не заменять знаменатель на маленький epsilon |
| 95 профилей без текущего тарифа | Не выдумывать тариф; учитывать отдельно при оценке доступного охвата |
| 5 пропусков ARPU-сегмента, 110 пропусков data-сегмента | Для MVP не включать в соответствующие сегментные гипотезы; отразить исключения в отчёте |
| 350 повторяющихся ключей «абонент × месяц» в месячном ARPU | Не делать many-to-many join; если таблица понадобится, сначала выяснить и описать политику агрегации |
| У 13 337 профилей LTE-трафик больше общего трафика | Не использовать отношение LTE/общий трафик как надёжный признак |
| Сильные выбросы ARPU | Робастные исторические агрегаты; экономический вес `predicted_arpu` для скоринга не обрезать |

В текущем профиле нет пропусков ID и `predicted_arpu`; 481 строка имеет хотя бы одно пустое поле. Это не повод удалять все 481 профиля: необходимые признаки выбираются отдельно. Среду и её исходный профиль не исправлять на месте. Локально заполненные признаки могут использоваться для ранжирования, но аудитория выводимой кампании должна соответствовать исходным фильтрам `env`.

Для MVP достаточно профиля, справочников и истории переходов. Месячные таблицы подключать, только если это даёт проверяемое улучшение: они содержат чужую для финальной аудитории историю и увеличивают объём подготовки.

## Размеры сегментов

| Разбиение | Число абонентов |
|---|---:|
| ARPU HIGH / MID / LOW / пропуск | 13 918 / 6 780 / 2 738 / 5 |
| Data HEAVY / LITE / NON_USER / пропуск | 11 735 / 10 253 / 1 343 / 110 |
| Calls LOW / MEDIUM / HIGH | 10 716 / 8 309 / 4 416 |
| HIGH × HEAVY | 8 937 |
| HIGH × LITE | 4 829 |
| MID × LITE | 3 733 |
| MID × HEAVY | 2 348 |

Например, `HIGH × HEAVY` больше лимита кампании. Его стоит делить допустимыми фильтрами текущего тарифа или звонков. При автоматическом отсечении среда берёт первые ID, а не самые доходные профили. Расчёт ожидаемой выгоды должен учитывать реальный состав выбранной аудитории.

HIGH-численности из идеи друга подтверждены: `tariff_8` — 4 726, `tariff_10` — 2 950, `tariff_4` — 2 108, `tariff_11` — 1 633; вместе **11 417**. Это ценные кандидаты для разведки, но HIGH сам по себе не подтверждает прибыльность перехода. Эффект конкретного target нужно проверять пилотом.

Дополнительный воспроизводимый аудит: **63** ячейки с заполненными текущим тарифом и ARPU-сегментом, ни одна не больше 5 000. Они дают **1 260** действий на другой тариф, из которых история после удаления точных дублей и неположительного предыдущего ARPU поддерживает только **456 (36,19%)**. Безусловный отсев ячеек меньше 150 человек исключает 42 ячейки, 1 345 профилей и 6,79 млн базовой ARPU. Скрипт и метод приведены в исследовании `research/03-priors-and-validation.md` и `research/experiments/priors_audit.py`.

## Какие выводы история не подтверждает

История содержит только состоявшиеся переходы, без контрольной группы, отказов и каналов коммуникации. Поэтому по ней нельзя честно определить причинный прирост кампании, вероятность отклика на предложение или превосходство SMS над звонком. Разность ARPU до/после — описательная характеристика уже перешедших клиентов.

При подготовке исторических признаков использовать только сведения до перехода. `AVG_ARPU_NEXT_3M` — результат, который объясняем, а не входной признак. ID не использовать как обучающий признак. Для текущей аудитории численные оценки действий уточнять разрешёнными пилотами.

## Расхождения и тонкости документов

- В описании заявлено 14 824 перехода, в файле 14 823 строки. Для расчётов брать фактическое число.
- Основное ТЗ допускает 10 минут, комментарий шаблона упоминает 5. Внутренний дедлайн 4 минуты укладывается в оба ориентира.
- При запуске агентской оценки пилоты учитываются перед финальными кампаниями: [local_eval.py](<../amir-research/local_eval.py#L45>).
- Повторный контакт расходует ресурс, а эффект берётся один раз по лучшему предложению: [scoring_core.py](<../amir-research/scoring_core.py#L241>).
- Стандартный результат пилота не содержит ID и всех фильтров. Агенту нужен собственный журнал: [environment.py](<../amir-research/environment.py#L183>).
- Таблица баллов 25/25/25/15/10 присутствует в переданном вставленном тексте; в прочитанном четырёхстраничном PDF она отсутствует. В плане защиты она учтена именно как часть предоставленных пользователем материалов.
