# Исторические priors, покрытие кандидатов и проверка переноса

Дата проверки: 23 сентября 2026. Рекомендация: оставить `azamat-reserch-codex` основой. Его трактовка истории, неизвестных тарифов и проверки на разных мирах точнее. Из Claude перенести компактный собственный `prior.csv`, включённый в сдаваемый комплект. Ниже — проект решения, а не измеренное превосходство реализованного агента.

## 1. Что подтверждено данными

Метод: удалить шесть точных дубликатов переходов; для процентного изменения оставить положительный `AVG_ARPU_PREV_3M`; исторический сегмент восстановить порогами `<1000`, `1000…5000`, `>5000`; посчитать поддержку `(from, segment, target)`. Текущие ячейки строить только по заполненным `current_tariff` и `arpu_segment`. Индивидуальные ID не публиковались.

## 2. История не оценивает отклик на кампанию

Доля переходов на target среди уже перешедших — распределение выбранных тарифов, а не вероятность принятия предложения среди всех контактов. В CSV отсутствуют предложения, отказы, канал и вероятность назначения действия. Поэтому ни propensity weighting, ни «доля переходов как конверсия» не восстанавливают контрфактический результат. В формализованном обучении по журналам действий требуется учитывать политику, породившую наблюдения; журнал не даёт исходов невыбранных действий. [Swaminathan и Joachims, §3–4](https://proceedings.mlr.press/v37/swaminathan15.pdf).

Отдельно различать смену состава аудитории и смену реакции при одинаковых признаках. Importance weighting исправляет covariate shift при сохранении условного распределения результата; гарантии не покрывают произвольную смену эффектов. Организаторы допускают отличающиеся эффекты, поэтому переобучение или перевзвешивание истории не заменяет пилоты. [Sugiyama и соавторы, определение covariate shift](https://jmlr.csail.mit.edu/papers/volume8/sugiyama07a/sugiyama07a.pdf).

Для MVP история задаёт **ранг гипотез**, численный prior эффекта контакта остаётся около нуля. Стартовая проверяемая настройка на SMS-шкале: `Normal(0, 0.25²)`; чувствительность — масштабы 0.15 и 0.50. При опубликованном шуме 0.804 масштабы 0.15/0.25/0.50 эквивалентны приблизительно 29/10/3 контактам; тысячи исторических строк не превращаются в тысячи фиктивных пилотов. Это инженерные настройки, не оценённые из CSV параметры. Проверять изменение состава плана, выбранных target и net при смене prior. Проверки влияния priors и моделирование искусственных данных — часть рекомендуемого статистического workflow. [Gelman и соавторы, §4 и §6.3](https://arxiv.org/pdf/2011.01808).

## 3. Лёгкий генератор target без зашитых победителей

Все тарифы получать из `env.tariffs`; исключение `target == current` — явное бизнес-правило отсутствия смены. Полный каталог из 1 260 агрегированных действий мал: хранить его целиком дешевле, чем преждевременно исключать 12 неизвестных целей. Таблица «клиент × тариф» не нужна.

Для каждой ячейки подготовить четыре источника кандидатов:

1. Лучший исторический ранг: медианное относительное изменение после очистки с поддержкой и сглаживанием к общему направлению. Это очередь исследований, не прогноз прибыли.
2. Ближайший более дорогой тариф: дистанция по `log1p(price)`, пакету интернета и минутам, признаки масштабированы по справочнику. Потребление ячейки помогает выбирать сопоставимый пакет; недостаток пакета — штраф ранга, не запрет.
3. Сопоставимый по цене или более дешёвый тариф с другим пакетом. Увеличение цены само по себе не доказывает рост ARPU.
4. Ещё не исследованный target вне исторического покрытия: выбрать наиболее отличающийся по тем же признакам; при равенстве использовать фиксированный генератор случайности.

Дубликаты убрать. Очередь 30–40 действий собирать из ценных ячеек по сумме `predicted_arpu`, сохраняя несколько мест для MID/LOW и неизвестных целей. После отрицательных пилотов пополнять очередь из полного каталога. Зафиксировать минимум два обзорных пилота для структурно иных гипотез; это ограничивает зависимость поиска от исходного ранжирования, но не гарантирует нахождение лучшего из 1 260 действий за 20 пилотов. Не использовать названия `tariff_9`/`tariff_21` как признаки качества. `prior.csv` хранит агрегаты, support и версию подготовки; при его отсутствии генератор работает по справочнику.

## 4. Какие ячейки можно объединять

По [публичной модели](<../../amir-research/environment.py>) коэффициент определяется `from × arpu_segment × target × channel`. Data/call-подгруппы одной такой ячейки разделяют оценку коэффициента, хотя имеют разный абсолютный ARPU. Это позволяет делить исполнение без повторного обучения эффекта.

Разные исходные тарифы автоматически не объединять для статистики. Несовпадение знаков может исчезнуть в среднем. Смешанный пилот возвращает среднее коэффициентов по людям, тогда как прибыль взвешивается ARPU; перенос этого среднего на богатую подгруппу необоснован.

Для финальной упаковки допустимо объединить отдельно оценённые ячейки с одинаковыми ARPU-сегментом, target и каналом через `filter_current_tariff="a;b;c"`. Пересчитать аудиторию, лимиты и сумму `Σ μ_cell × ARPU_cell − cost`, не усредняя проценты без весов. Объединение не создаёт новую информацию. Если зависимость оценок неизвестна, использовать сумму отдельных нижних оценок как осторожную эвристику, не как строгую совместную доверительную границу. В MVP с десятью слотами это полезнее сложной иерархической модели. Позже — partial pooling с проверкой неоднородности и явной неопределённостью общего уровня.

## 5. Независимые миры для проверки

Тестовый harness создаёт собственную таблицу `impact_model` и передаёт её в публичную `make_environment`; агент получает только `env`. Оценщик использует `score_campaigns` и исполненные пилоты, доступные только harness. Таблицы эффектов не строить из mock-победителей. Оригинальные файлы среды не менять. Формула мира: `q × min(p × multiplier, 1)`, где `q` — изменение ARPU, `p` — синтетическая вероятность отклика. Это сценарные значения, не найденная историческая конверсия.

| Мир | Конструкция через публичную фабрику | Что проверяет |
|---|---|---|
| Разреженные возможности | 10% действий имеют q=0.4, остальные −0.1; p=0.5 | Разведку и отказ от масштабирования минуса |
| Обманчивая история | Верхние исторические ранги получают q=−0.25; независимые альтернативы +0.3 | Способность отбросить prior |
| Неизвестный победитель | q=+0.4 только у целей без исторической поддержки | Реальное исследование вне девяти target |
| Почти нулевой рынок | q∈{−0.02,0,+0.02}, p=0.5 | Контактные затраты и остановку |
| Все действия вредны | q=−0.15, p=0.5 | Ограничение ущерба при обязательной кампании |
| Обратная ценность сегментов | HIGH: q=−0.15; часть MID/LOW: +0.4 | Отказ от безусловного HIGH-only |
| Разные знаки внутри объединения | Соседние from получают ±0.3 | Ошибочное объединение наблюдений |
| Насыщение канала | q=0.3, p=0.95 | Нелинейность переноса на call |

В пятичасовом MVP после официальных проверок начать с двух собственных миров: «обманчивая история» и «все действия вредны». Если тестовый harness уже готов и есть время, расширить до первых четырёх миров плюс всех отрицательных действий, по три pilot-seed. Позже добавить остальные, несколько независимо созданных таблиц на семейство, усиленный шум и ошибки API через отдельный совместимый test double. Менять seed при неизменной таблице — проверять шум наблюдений, а не перенос между мирами. Матрица здесь спроектирована; полноценные прогоны агента на ней ещё не выполнены.

## 6. Как не переоценить результат

Сначала зафиксировать семейства сценариев, затем выбирать из максимум трёх конфигураций на development-мирах. Другой участник создаёт новые таблицы и seed для финальной проверки. Сравнивать шаблон, фиксированную разведку, адаптивную разведку и вариант без исторического ранга; использовать одинаковые миры. Отчёт: средний/медианный net, худший сценарий, число отрицательных прогонов, стоимость разведки, охват, время и нарушения лимитов. Для малых трёх повторов не выдавать устойчивую оценку хвостового риска.

В собственных синтетических мирах отдельно измерить потерю от генератора: насколько лучший доступный в shortlist target хуже лучшего по полному каталогу для каждой ячейки. Это диагностика с известной тестовой истиной, которую агент не видит; она отделяет слабый поиск кандидатов от слабого выбора пилотов. Полный oracle с бюджетными ограничениями — позже. Исторический holdout измеряет только перенос описательных pre/post-закономерностей; назвать его проверкой прибыли кампаний нельзя.
