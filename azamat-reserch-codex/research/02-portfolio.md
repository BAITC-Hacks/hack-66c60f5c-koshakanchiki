# Портфель кампаний: какую основу выбрать и что улучшить

Дата исследования: 23 сентября 2026. **Выбор — `azamat-reserch-codex`.** Его ограничения API, сравнение push/SMS/ads, насыщение call и осторожность статистических обещаний корректнее. В `azamat-reserch/01-strategy.md` полезна идея дискретного выбора каналов, но «всем SMS, затем дорогие улучшения» теряет выгодные сочетания. Также нельзя гарантировать стабильный знак при `z≈1`, а близкие наблюдения SMS/ads не доказывают насыщение: при вероятности конверсии ≤1 оба множителя меньше единицы. Байесовские веса в текущем документе конкурирующей папки уже правильные — это не основание его отвергать.

Главное улучшение выбранной основы: **один точный симулятор исполнения публичных фильтров + несколько жадных стартов + короткий поиск замен**. Точно воспроизводится механика; будущие эффекты остаются оценками.

## 1. Что именно можно оптимизировать

Публичный скоринг сначала применяет фильтры, сортирует по `ID_NUMBER`, ограничивает строку 5 000 людьми, затем остатком контактов и денег. Он не выбирает самых прибыльных людей внутри фильтра. Повторные контакты расходуются полностью, эффект учитывается один раз по лучшей кампании. Пилоты предшествуют финальным строкам. [Порядок исполнения](<../../amir-research/scoring_core.py#L195>), [дедупликация](<../../amir-research/scoring_core.py#L241>), [пилоты плюс финал](<../../amir-research/local_eval.py#L48>).

Следовательно, предмет выбора — **исполняемые строки с фильтрами**, а не произвольные списки ID или дробные размеры. Для каждой строки заранее сохранить отсортированные ID и префиксные суммы `predicted_arpu`: если поместились `m` человек, использовать сумму первых `m`, а не `m × среднее` всей аудитории. В MVP выбирать непересекающиеся полные блоки, которые совместно помещаются в остатки; при запасе времени разрешить последнюю усечённую строку и оценивать её симулятором.

Блок — тариф × ARPU-сегмент, при необходимости разделённый допустимыми data/call-фильтрами. Целая ячейка и её дочерние фильтры — взаимоисключающие варианты. «Удалить уже выбранные ID» из очередного фильтра невозможно: следует отклонить пересекающийся вариант или действительно изменить фильтры. Детализация не бесплатна: даже маленький блок расходует одну из десяти строк.

## 2. Добавочная прибыль и неизвестные ID пилотов

Без предыдущих контактов оценка блока равна `r × сумма ARPU − c × n`, где `r` уже включает канал. Для ранжирования можно подставлять `r = mean−k×sd`; это осторожная эвристика, а не гарантия знака портфеля. Стоимость ранее проведённых пилотов уже понесена: её показывают в общем результате, но не вычитают заново при каждом сравнении финальных вариантов.

Пилотные ID не возвращаются публичным API. При равномерных независимых выборках одной ячейки из `N` человек вероятность хотя бы одного предыдущего контакта оценивается как `p=1−∏(1−n_j/N)`. Для повторения **того же предложения и канала** добавочный валовый эффект финала приблизительно `(1−p)r × сумма ARPU`, а платить приходится за все финальные контакты. Это вероятностная оценка пересечений, не восстановление фактических ID. [Публичный контракт пилота](<../../amir-research/environment.py#L131>).

При смене target или канала одного дисконта недостаточно. Если предыдущая лучшая оценка эффекта для уже контактированного человека — `b`, добавка равна `max(r,b)−b`; для ранее не контактированного — `r`. Усреднить эти две ситуации по вероятностям. При нескольких пилотах распределение максимального эффекта строится по отсортированным оценкам и вероятностям включения; для разных фильтров расчёт вести на их атомарных пересечениях. Это остаётся приближением, поскольку сами `r` и `b` оценены с ошибкой. Для пяти часов допустимо сначала реализовать одинаковое предложение и честно маркировать упрощение остальных пересечений.

## 3. Канал выбирается вместе с аудиторией

Пусть `v=ARPU × u`, где `u` — эффект без множителя канала. Для положительного эффекта:

```text
push: 0.50v; SMS: 0.65v−4; ads: 0.85v−22.
```

При свободном бюджете SMS выигрывает у push при `v>26.67`, ads у SMS при `v>90`. При дефиците денег этого недостаточно: один большой ads-блок может вытеснить несколько более полезных действий. Заменять SMS на ads стоит дополнительно `18n`, а запускать ads поверх уже отправленной SMS — `22n` и ещё `n` контактов. [Формула каналов](<../../amir-research/scoring_core.py#L145>).

Для осмысления альтернативной стоимости использовать

```text
utility = Δnet − λ_money·Δcost − λ_contacts·Δcontacts − λ_rows·Δrows.
```

Коэффициенты показывают ценность дефицитного ресурса. При замене канала той же аудитории контакты не меняются; условие SMS→ads становится `0.20v > 18(1+λ_money)`. В целочисленной задаче подобранные вручную коэффициенты — только ранжирование. Настоящие двойственные оценки можно получить из непрерывного ослабления; локальная чувствительность требует соответствующих математических условий. [Boyd–Vandenberghe, раздел 5.22–5.25](https://stanford.edu/~boyd/cvxbook/bv_cvxslides.pdf).

Call оставить за пределами MVP: `min(conversion×1.20,1)` не позволяет точно переносить SMS-эффект одним множителем. Для его включения нужен отдельный пилот или консервативная модель насыщения. Это ограничение срока разработки, не вывод о бесполезности звонков.

## 4. Практичный поиск за пять часов

1. Построить 20–40 вариантов фильтров; для пилотированных гипотез оценить push/SMS/ads и вариант отказа. Удалять доминируемые альтернативы только при одинаковой аудитории и не больших расходах ресурсов.
2. Собрать 3–4 начальных плана: жадно по суммарному добавочному net; по net на контакт; по net на нормированный расход `n/H + cost/B + rows/10`; сохранить также простой SMS-план. Каждый шаг проверяет конфликты фильтров и фактические ресурсы.
3. Выбрать лучший по одной оценочной функции. Проверить смену канала/target, добавление и удаление строки, обмен одной строки на две из короткого списка. После изменения пересчитать весь план; принимать только строгое улучшение. Ограничить поиск числом проверок и дедлайном.
4. Если допускаются усечения, проверить несколько порядков строк и соседние перестановки. Улучшение канала способно изменить остаток денег и усечь следующие кампании: нельзя оценивать его изолированно.
5. Вернуть лучший уже проверенный вариант. Отдельно вывести оценку net, модельную неопределённость, расходы и причины остановки. Это локальный поиск без гарантии глобального оптимума.

## 5. Маленькая воспроизводимая проверка

Исполнен [portfolio_toy.py](<experiments/portfolio_toy.py>), результаты — [JSON](<experiments/portfolio_toy_results.json>). Команда: `python3 azamat-reserch-codex/research/experiments/portfolio_toy.py`.

20 фиксированных seeds 0–19; восемь непересекающихся синтетических блоков по 500–4 500 человек; четыре варианта: пропустить/push/SMS/ads. Остатки — 12 520 контактов и 90 080 денег, максимум десять строк. Полный перебор проверяет `4⁸=65 536` комбинаций на случай. Все блоки выбираются целиком; базовые эффекты в генераторе положительные. Восемь блоков не активируют лимит десяти строк. Здесь нет усечения, пилотов, пересечений, неопределённости или скрытой модели организаторов: проверяется только дискретный оптимизатор, не готовый агент.

| Метод | Среднее от точного максимума | Худший случай | Совпал с максимумом |
|---|---:|---:|---:|
| Сначала SMS, затем жадные ads | 97.424% | 89.217% | 7/20 |
| Лучший из четырёх стартов | 99.454% | 94.208% | 18/20 |
| Затем изменения до трёх блоков | 100% | 100% | 20/20 |

В seed 6 исходный вариант дал 6 097 815 условных единиц, улучшенный — 6 834 838. Первый запуск всего эксперимента занял около 1.86 секунды; независимый повтор — около 2.24 секунды с теми же значениями целевой функции. Совпадение на двадцати небольших задачах **не доказывает оптимальность алгоритма** и ничего не обещает о хакатонном балле; оно показывает конкретную потерю схемы «сначала всем SMS» и пользу дешёвых замен.

## 6. Что развивать после MVP

Для непересекающихся полных блоков задача задаётся бинарными переменными `x[block,channel]`: максимум оценочного net, не более одного канала на блок, суммы контактов/стоимости/строк в пределах остатков. Варианты пересекающихся фильтров дополнительно запрещаются попарными ограничениями. Это MILP для **ограниченного набора вариантов**, а не точное решение исходной задачи с неизвестными эффектами и любым порядком усечения.

`scipy.optimize.milp` позволяет задать лимит времени и допустимый относительный разрыв; проверять наличие решения, статус и `mip_gap`, затем валидировать ресурсы. При таймауте сохранять лучший допустимый эвристический план. [Официальная документация SciPy](https://docs.scipy.org/doc/scipy/reference/generated/scipy.optimize.milp.html).

DP с состоянием `(бюджет, контакты, число строк)` при исходной точности слишком велико для простой плотной таблицы. Разреженный фронт недоминируемых состояний или округление ресурсов возможны, но добавляют реализацию и требуют повторной точной проверки. В пятичасовой срок предпочтительнее несколько стартов и локальные замены; MILP — последующее сравнение, когда симулятор и оценка эффекта уже проверены.
