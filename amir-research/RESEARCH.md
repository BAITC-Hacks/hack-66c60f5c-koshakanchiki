## 1. Задача в двух словах

Дано 23 441 абонент, 100 000 у.е. бюджета, до 10 финальных кампаний, до 20 пилотов.
Нужно написать `agent.py` с классом `Agent.act(env) -> list[dict]`, который решает:
**кому** (сегмент), **что** предложить (один из 21 тарифа), **как** (канал: push /
sms / digital_ads / call) — так, чтобы максимизировать чистый результат:

```
Чистый результат = Прирост ARPU (по уникальным абонентам) − Затраты на контакты
```

Если ничего не делать — база и так принесёт 150 641 084 (сумма `predicted_arpu`).
Побеждает тот, у кого чистый результат (прирост минус затраты) больше.

## 2. Главная механика: разведка вслепую (explore/exploit)

- Выданная история (`data/change_tariff.csv`) — **про другую выборку абонентов**,
  не про тех 23 441, на которых считается результат. Это только априорная подсказка
  "как обычно бывает", не готовый ответ.
- Единственный способ узнать правду про ИМЕННО ЭТУ аудиторию — пилот
  (`env.run_pilot(...)`): маленькая реальная кампания на 10–200 человек.
- Пилот стоит денег и охвата **из общего бюджета** — разведка не бесплатна.
- Пилот **зашумлён**: стандартное отклонение эффекта на одного абонента
  `PER_CUSTOMER_STD ≈ 0.804` (задокументировано прямо в `environment.py`, это не
  секрет модели — секрет только сами эффекты). Шум среднего по выборке пилота:

  ```
  std(наблюдаемый эффект) ≈ 0.804 / √n
  ```

  При n=30 → ±0.15; при n=150 → ±0.066; при n=200 → ±0.057. Типичный реальный
  эффект — 0.2–0.45. То есть маленький пилот почти ничего не говорит сам по себе —
  нужно либо комбинировать с историческим prior, либо доливать вторым, более крупным
  пилотом на многообещающих кандидатах.
- Стратегия без разведки (действовать только по истории) приносит, по условию
  кейса, **в ~15 раз меньше**, чем стратегия, знающая истинные эффекты.

## 3. Как считается эффект (важно для дизайна агента)

`environment.py` / `scoring_core.py` считают эффект кампании как:

```
lift_ratio = arpu_change_pct(тариф_из → тариф_в, ARPU-сегмент)
           × min(1.0, conversion_rate × channel.conversion_multiplier)

expected_lift_per_customer = lift_ratio × predicted_arpu(абонента)
```

Следствия для дизайна:

- Эффект **относительный** (доля от ARPU конкретного абонента) — один и тот же
  переход на дорогом абоненте стоит больше. `predicted_arpu` уже посчитан
  организаторами и лежит в `customer_profile.csv` — использовать его как базу
  ценности сегмента.
- Канал не меняет сам % изменения ARPU — он меняет **вероятность, что абонент
  вообще отреагирует** (`conversion_rate × multiplier`, не выше 1.0). Дорогой канал
  (`call`, 160 у.е./контакт, ×1.20) оправдан только там, где эффект и ARPU сегмента
  достаточно велики, чтобы окупить стоимость контакта.
- **Дедупликация**: каждый абонент учитывается один раз — по лучшей для него
  кампании. Повторный контакт всё равно стоит денег, но лифт не удваивается —
  нет смысла бить по пересекающимся сегментам несколькими кампаниями.
- Порядок кампаний в списке имеет значение: `scoring_core` обрабатывает их по
  порядку и обрезает по бюджету/охвату, когда лимит кончился — значит **сортировать
  финальный список по убыванию ожидаемой ценности**, лучшие кампании должны идти
  первыми.

Каналы (`environment.py`, не меняются):

| Канал | Стоимость контакта | Множитель конверсии |
|---|---|---|
| `push` | 0 | ×0.50 |
| `sms` | 4 | ×0.65 |
| `digital_ads` | 22 | ×0.85 |
| `call` | 160 | ×1.20 |

## 5. Что уже посчитано (proof of concept, не для копирования в проект)

Прогнал черновой алгоритм на локальной мок-среде (`mock_environment.py`, реальные
эффекты на судействе — другие, это только проверка механики):

- Идея: исторический prior из `change_tariff.csv` (средний % изменения ARPU ×
  доля перешедших именно на этот тариф, по ячейке тариф×ARPU-сегмент) → ранжируем
  ячейки аудитории → пилотируем топ-кандидатов маленькой выборкой (n=30) →
  байесовски комбинируем prior и наблюдение (взвешивание по обратной дисперсии,
  используя тот же `PER_CUSTOMER_STD=0.804`) → самых многообещающих, но ещё
  неуверенных кандидатов дозондируем вторым пилотом покрупнее (n=150) → по
  posterior-оценке выбираем канал (экономика на клиента) и собираем до 10
  финальных кампаний.
- На `python local_eval.py --runs 10` (10 разных seed): **все 10 прогонов в
  плюс**, чистый результат от +618 тыс. до +1.58 млн (медиана ~736 тыс.),
  знак ни разу не менялся. Это проверка **устойчивости алгоритма**, не будущего
  балла — эффекты в моке ненастоящие.
- Черновой код прототипа лежит отдельно, вне этого репозитория
  (`/home/user/hackalem-beeline/agent.py`) — использовать только как референс
  идеи при реализации, не копировать as-is: там нет ревью, нет обработки краевых
  случаев на 100%, часть числовых порогов (`MIN_CELL_SIZE`, размеры пилотов и т.д.)
  подобрана на глаз и требует проверки на реальной задаче.

## 6. Открытые вопросы / риски на этап реализации

- Наш prior из `change_tariff.csv` — это **своя эвристика**, не официальная
  "формула эффекта". Реальная модель на судействе другая (`environment.py`,
  строки 1–20) — нельзя подгонять константы под мок.
- `conversion_rate`, которую мы оцениваем по истории как "доля ушедших именно на
  этот тариф из тех, кто вообще менял тариф", — это **не то же самое**, что
  "вероятность, что абонент откликнется на проактивное предложение по каналу".
  Это единственная доступная прокси-оценка, но её нужно относиться к ней как к
  грубому приоритету для пилотов, а не как к точному числу.
- Неясно, будет ли доступен `data/change_tariff.csv` в момент прогона на судействе
  (в списке обязательных артефактов — только `agent.py`, `submission.csv`,
  `requirements.txt`). Агент должен **не падать**, если файла нет — работать
  только на пилотах в этом случае (заложить try/except при чтении).
- Агент обязан укладываться в 10 минут работы **включая все вызовы модели** —
  если решим использовать LLM в контуре, это добавляет риск таймаута/ошибки API;
  обсудить масштаб использования LLM отдельно на этапе дизайна (см. `PLAN.md`).
