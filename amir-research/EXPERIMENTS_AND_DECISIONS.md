# Решения для реализации и план проверок после ресёрча

Дата: 23.09.2026. Это план следующих экспериментов, а не отчёт об уже достигнутом балле. В рамках исследования выполнены профиль данных и проверки механики; новый соревновательный агент не реализован.

## 1. Предлагаемая первая версия

1. Взять фактические `env.customer_profile`, `env.tariffs`, `env.channels`, остатки ресурсов. Анализировать копии; не изменять среду.
2. Построить 63 известные ячейки `current_tariff × arpu_segment` и доступные подгруппы. Отдельно учитывать пропуски. Вычислять размеры, суммы ARPU, допустимые ID-префиксы.
3. Получить слабые априорные оценки переходов из истории, если этот файл доступен. При отсутствии истории использовать широкий prior и признаки справочника. Не выдавать частоту перехода за измеренную response probability.
4. Сократить 1 260 пар «известная ячейка → другой тариф» до исследуемого пула. Сохранять альтернативы вне исторического лидера и разнообразие целевых тарифов.
5. Пилотировать однородные ячейки. Сохранять собственные фильтры, канал, реальное n, наблюдение и время. Обновлять Gaussian posterior с корректной дисперсией канала.
6. Выбирать следующие пилоты по вероятности и денежному масштабу изменения конечного портфеля. Сначала допустима простая фазовая схема; её сравнить с адаптивной.
7. После каждого значимого наблюдения пересчитывать доступные прибыльные кампании, каналы и ресурсы. Для call учитывать насыщение.
8. Вернуть 1–10 валидных кампаний с документированными фильтрами. Объединять совместимые тарифы только после пересчёта охвата/обрезки. Удерживать запас времени на сборку результата.
9. Отдельно проверить экспорт фиксированного seed, зависимости, наличие файлов и README.

Это инженерный выбор по результатам [аудита](LOCAL_CODE_DATA_AUDIT.md), [исследования методов](EXTERNAL_PILOT_METHODS.md) и [экономики](CAMPAIGN_ECONOMICS.md). Оптимальность конструкции не установлена.

## 2. Что сравнивать в первую очередь

| Приоритет | Гипотеза | Контроль | Что покажет эксперимент |
|---|---|---|---|
| P0 | Правильная обработка результата пилота | Точное ручное Gaussian-обновление | Не потеряли ли `n_actual`, множитель и variance |
| P0 | Портфель выполним в реальном API | Публичный scorer на своём сценарии | Совпадают ли охват, ID-cap, деньги, число строк |
| P1 | Слабый prior лучше чрезмерно уверенного | Нулевой/широкий prior, сильный prior | Может ли агент пересмотреть ошибочную историю |
| P1 | Дозирование пилотов улучшает net | Фиксированные n и список кандидатов | Окупается ли адаптация |
| P1 | SMS-пилоты окупают точность | Push-пилоты при том же лимите вызовов | Цена денег против контактов и слотов |
| P1 | Денежный приоритет лучше максимального ratio | Ранжирование по raw ratio | Учитывается ли масштаб аудитории |
| P1 | Отдельная обработка call необходима | Безусловный множитель 2.4 от push | Ошибка при конверсии выше 5/6 |
| P2 | Локальный поиск улучшает жадный портфель | Простой допустимый greedy | Выигрыш от бюджета/порядка/слотов |
| P2 | Частичный обмен информацией помогает | Независимые ячейки | Отрицательный перенос между похожими тарифами |
| P2 | Остановка раньше 20 иногда полезна | Всегда 20 пилотов | Предельная стоимость поздних измерений |

Полный перебор всех параметров на одной mock-модели не является нужной проверкой. Сначала выбрать небольшое число содержательных альтернатив и оценить их на нескольких типах мира.

## 3. Набор синтетических миров для стресс-проверки

Модели ниже создаются нами вне `Agent.act`, передаются в публичную фабрику среды и остаются неизвестными агенту. Это проверочный стенд, а не чтение скрытых эффектов. Сохранять отдельный seed генерации мира и seed наблюдений.

| Мир | Как задаётся | Какой провал ищем |
|---|---|---|
| Близкий к prior | Умеренная случайная вариация исторических гипотез | Не слишком ли дорого обходим простой baseline |
| Слабый сигнал | Эффекты близки к нулю | Перерасход бюджета и выбор шумных победителей |
| Ошибочный знак | Часть исторически лучших переходов становится отрицательной | Способность отказаться от prior |
| Редкий хороший тариф | Хороший эффект у неисторического лидера | Недостаточное исследование альтернатив |
| Сдвиг по ARPU | MID лучше HIGH по относительному/денежному эффекту | Жёсткий хардкод «работать только с HIGH» |
| Высокая конверсия | `c>5/6` на части действий | Неверная линейная экстраполяция call |
| Неоднородная смесь | Разные тарифные ячейки имеют разные знаки | Ошибка оценки денежного эффекта смешанного пилота |
| Схожие тарифы, разные эффекты | Одинаковое наполнение, противоположные реакции | Чрезмерная иерархическая связь |
| Крупные пересечения | Много выгодных фильтров на одних людях | Двойной счёт эффекта и повторная оплата |
| Малые остатки ресурсов | Очень дорогие ранние действия/малые группы | Неправильный n, падения, пустой финал |

Нет причин считать распределение этих миров совпадающим с финалом. Их назначение — находить логические слабости. При отрицательных эффектах всех возможных действий положительный результат может быть недостижим: требование «всегда плюс» не доказываемо.

## 4. Метрики и воспроизводимость

Для каждой пары «мир × seed наблюдений» фиксировать:

- итоговый `net_arpu_gain`, gross и расходы;
- число финальных кампаний, пилотов, контактов и уникальных людей;
- частоту отрицательного net, медиану и нижний квантиль по серии;
- долю случаев, когда пилот поменял выбранный тариф/канал/портфель;
- время выполнения и запас до десятиминутного лимита;
- неопределённость выбранных эффектов и денежную потерю от неверного выбора;
- недопустимые фильтры/действия, число исключений и сработавшие fallback.

Сравнивать стратегии на одинаковом наборе миров. Один seed среды не создаёт буквально одинаковые наблюдения при разных последовательностях действий: разные размеры/порядок пилотов меняют потребление RNG. Для статистики нужен достаточный набор прогонов, а не сравнение одной пары чисел.

Если рассчитывается oracle, его разрешения должны совпадать с ограничениями сравнения: те же фильтры, лимиты, обрезки, максимум 10 кампаний. Oracle без стоимости разведки полезен как верхняя планка; нельзя выдавать разницу с ним за чистую ошибку выбора, если он освобождён от обязательного пилота. Сильный поиск по сокращённому пулу кандидатов — benchmark, но не доказанный глобальный optimum всей задачи.

## 5. Обязательная инженерная проверка

Только после появления `agent.py`:

```bash
cd amir-research
python local_eval.py
python local_eval.py --runs 10
python make_submission.py
```

Затем проверить 1–10 строк, существующие каналы/тарифы, ожидаемые семь колонок, повторяемость `submission.csv` при повторном запуске и независимость от случайного состояния предыдущего вызова. Экспортёр сам не отбрасывает лишние/некорректные кампании так, как это делает `local_eval`.

`requirements.txt` должен явно описывать используемые зависимости. Пакеты, установленные для этого исследования в `/tmp`, не гарантируют такое же окружение судей. Проверки здесь выполнены на pandas 3.0.6 и NumPy 2.5.3; особенности обработки пропусков необходимо учитывать и при целевой версии зависимостей.

Исследование не воспроизводило результаты старого PoC, упомянутые в исходном `RESEARCH.md`: сам PoC находится вне папки проекта. Ранее записанные +618 тыс…+1.58 млн нельзя приписывать текущему исследованию или новому агенту.
