# Техническое решение для следующего этапа

**Статус:** спецификация будущего агента. Механика и отдельные формулы проверены; полный алгоритм, параметры разведки и его net ещё не испытаны. Начальные настройки ниже нужны для однозначной первой реализации и затем сравниваются по [плану проверки](VALIDATION.md).

## 1. Данные и кандидаты

Работать с копиями публичных `env.customer_profile`, `env.tariffs`, `env.channels`; текущие остатки брать из `env`. Не менять исходный профиль. Идентификаторы используются для совпадения механики фильтров, не как обучающий признак.

Ячейка `s=(current_tariff, arpu_segment)`. Хранить численность `N_s`, сумму baseline `A_s`, отсортированные по ID индексы и префиксные суммы `predicted_arpu`. Не обрезать baseline-выбросы: scorer использует исходные значения. 100 профилей с пропусками ключей отделить в отчёте; не включать их широким фильтром. Пропуск только data/call не мешает целой ячейке. Не вводить общий порог «минимум 150 клиентов».

Для каждого `s` каталог содержит все target из справочника, кроме текущего. Исключение self-target — выбранное правило задачи смены тарифа, не запрет `sanitize_campaigns`. Data/call-подгруппы разделяют оценку эффекта своей ячейки.

**Исторический ранг, офлайн:** удалить точные дубли, оставить `prev_ARPU ≥100`, сегментировать `pd.cut([-inf,1000,5000,inf])`. Для пары посчитать support и медиану `clip(next/prev−1,−1,3)`. Начальный сглаженный ранг `support/(support+10) × median`; сглаживание и пороги — гипотезы, не causal-модель. Сохранить агрегаты, схему, формулу и SHA-256 источника в `historical_candidates.json` рядом с кодом. Не переносить support в точность posterior.

Из каждого ценного сегмента брать четыре разных основания для target: лучший исторический ранг; ближайший более дорогой пакет; ближайший пакет с `price≤current_price` и иным наполнением; target без исторической поддержки. Близость: евклидова дистанция по четырём стандартизированным `log1p`-признакам справочника: `price_tariff`, `Data_in_PKG`, `Min_another_operator_in_PKG`, `Min_another_operator_and_city_in_PKG`. Стандартизировать по доступным тарифам, при нулевой дисперсии признак пропустить. Две колонки минут сохраняются отдельно; штрафы по потреблению в первой версии не вводить. Из неизвестных target выбрать наиболее удалённый для разнообразия; равенства разрешать по коду тарифа. Если категория пуста, перейти к следующей.

Очередь до 40 действий: ячейки по `A_s`, round-robin по четырём основаниям, максимум четыре действия одной ячейки. Первые восемь обзора: шесть лучших по этому порядку и два зарезервированных разных действия — одно вне HIGH, одно без исторического support. Кандидаты и ячейки не повторяются без причины; если категории исчерпаны, взять следующий допустимый вариант. Это обеспечивает присутствие альтернатив, не гарантирует хороший target. Если файл истории отсутствует/неверной схемы, использовать справочник и тот же нулевой prior, записав fallback в лог.

## 2. Единая шкала posterior

Для действия `a=(s,target)` параметр `θ_a` — истинный **SMS ratio**, уже включающий множитель SMS. Начало: `μ=0`, `v=0.25²`, независимые priors разных действий. Общие тарифные признаки не делают разные эффекты одинаковыми.

Пилот канала c даёт `y=observed_lift_ratio`, `n=actual_n`; при `c∈{push,sms,digital_ads}`:

```text
h = multiplier[c] / multiplier[sms]
R = 0.804² / n
y | θ ~ Normal(h θ, R)
v_new = 1 / (1/v + h²/R)
μ_new = v_new × (μ/v + h y/R)
```

Использовать старые `μ,v` в правой части. Отрицательный `y` не обнулять, observation не обрезать. Запрос 10 может фактически дать меньше 10; ответ `n≤0` или нечисловой `y` не включать в статистику. Нормализация наблюдения на h требует также деления R на h². Эквивалентность последовательного и суммарного обновления проверена в [verify.py](evidence/verify.py).

На выходе для канала c: `mean_ratio=hμ`, `sd_ratio=h√v`. Для SMS h=1: повторно умножать наблюдаемый SMS ratio на .65 нельзя. При одной нетронутой аудитории `S`:

```text
mean_net = h μ × Σ_S predicted_arpu − |S| × cost[c]
cautious_net = h (μ − k√v) × Σ_S predicted_arpu − |S| × cost[c]
```

Начать с k=1; сравнить k=0 и 1.64. Это модельный штраф за неопределённость, не гарантия покрытия/прибыли после адаптивного отбора. SE при n=120 равен .07339, при 200 — .05685; маленький пилот может менять знак из-за шума.

## 3. Пилоты: первая политика и challenger

**Первая политика:** SMS, одна ячейка, собственный журнал `request + result + time`. При сохранении исходных коэффициентов SMS даёт в 1.69 раза больше информации о θ на контакт, чем push, за 4 денег. Это обоснование исходного выбора, не доказательство оптимума.

| Этап | Верхняя граница | Правило |
|---|---:|---|
| Обзор | 8×120 | Разные действия из очереди с двумя резервами разнообразия |
| Уточнение | 4×180 | Пилотированное действие, неопределённость которого меняет выбор портфеля |
| Резерв | 4×200 | Продолжить нужное уточнение; при отсутствии перспективных проверенных действий — новый target из очереди |

Потолок всех этапов: 16 вызовов / 2 480 контактов / 9 920 SMS-денег. Это максимум, а не расход, который надо выполнить. Для непустой ячейки запросить `n_requested=max(10,min(размер_этапа,200,N_s))`; ожидаемый фактический размер `min(n_requested,N_s,remaining_contacts,remaining_budget//4)`. Проверить, что он положителен, помещается в проектный потолок и оставляет резерв финалу; иначе уменьшить допустимый запрос или остановиться. Ячейки N<10 не исключать автоматически: запрос 10 законно даёт меньший `actual_n`. Официальные 20 вызовов остаются верхним лимитом, оставшиеся четыре не расходуются автоматически.

**Конкретная начальная эвристика уточнения:** сохранить текущий портфель `P`. Для каждого уже пилотированного действия перестроить его дважды с `μ_a−√v_a` и `μ_a+√v_a` при остальных неизменных оценках. Сравнивать аудитории, target и каналы; имена/порядок строк сами по себе не считаются сменой решения. Если действие не меняет выбранные кампании, его приоритет 0. Иначе:

```text
v_after = 1 / (1/v_a + n_actual_expected/0.804²)  # SMS
priority(a) = A_reachable(a) × (sqrt(v_a) − sqrt(v_after))
```

`A_reachable` — максимальная сумма ARPU допустимой аудитории этой ячейки при текущих остатках, вычисленная через фильтры/ID-префиксы. Взять наибольший приоритет, равенства разрешить стабильным ключом. Это денежный масштаб уменьшения неопределённости, **не оценка окупаемости пилота**. Деньги и контакты учитываются в остатках и потолке; возможность невыгодных уточнений остаётся гипотезой для сравнения.

После восьми обзоров завершать, если приоритеты уточнения нулевые и уже есть положительный осторожный финальный вариант. Если все проверенные варианты неперспективны даже при `μ+√v`, использовать резерв для альтернатив, включая MID/LOW и неизвестные target, а не повторять проигравшего. Если уточнения исчерпаны, резерв не обязателен. Это правило проверяет конечную очередь при выбранном масштабе возмущения; оно не доказывает отсутствие неоткрытого победителя.

До первого вызова построить непустой допустимый fallback. Оставлять достаточно контактов для его исполнения; при SMS-режиме проектный потолок разведки оставляет минимум 12 520 контактов и 90 080 денег. После каждого ответа пересчитать план с новыми остатками. Прекратить при отсутствии ресурсов, исчерпании потолка, ошибке состояния или дедлайне. В обычном исправном окружении обязателен хотя бы один успешно выполненный пилот.

**Challenger, включать после сравнения:** одношаговая ценность пилота, как у Амира/Азамата:

```text
V(D,H,R) = оценка общего net выбранного плана с учётом пилотов
G(a,n) = E_Y[V(update(D,Y), H+(a,n), R−(4n,n))] − V(D,H,R)
Y ~ Normal(μ_a, v_a + 0.804²/n)
```

7 узлов Gauss–Hermite; n∈{120,200}; около нулевого G сверить 15 узлами. Считать на коротком списке кандидатов, использовать тот же портфельный критерий, что на выходе. Пилотный эффект и стоимость уже внутри V; второй раз их не добавлять. Стоп при `max G≤0`. Текущий toy выявил проигрыш на слабом положительном сигнале — нет основания заранее заменить им базовую политику.

## 4. Каналы и точное исполнение

При корректных вероятностях конверсии 0…1 push/SMS/ads линейно связаны. Если g — SMS gross на человека, то:

| Канал | Net на человека без предыдущих контактов |
|---|---:|
| push | `(0.50/0.65)g` |
| sms | `g−4` |
| digital_ads | `(0.85/0.65)g−22` |

Без дефицита денег SMS выгоднее push при g>17.333; ads выгоднее SMS при g>58.5. При общих лимитах это только проверка арифметики: нужно сравнивать целые планы. Для отрицательного ratio более сильный канал усиливает ущерб.

**Call в первой версии выключен.** Дешёвые каналы идентифицируют произведение d×q, а call при q>5/6 насыщается. В воспроизведённом примере одинаковые cheap ratios .10/.13/.17 совместимы с call .24 и .20. Для включения нужны прямой пилот или модель допустимых границ и сравнение общего net с его дорогой разведкой.

`simulate_plan` получает только публичный профиль, список строк, остатки и оценки. Для каждой строки: фильтры → ID-sort → первые 5000 → остаток контактов → `floor(остаток_денег/cost)` для платного канала → списание. Для push денежного деления нет. Считать ARPU фактического префикса, не `n×среднее` полной группы.

Финальные строки содержат только семь экспортируемых полей из [make_submission.py](../project-context/case-files/make_submission.py#L23). Нет финального `n_customers`, произвольного исключения ID или пользовательского `explicit_ids`. Отсутствующие фильтры — Python `None`, не `pd.NA`/строка `nan`.

## 5. Пилотные пересечения и критерий портфеля

Точный состав **финальных** аудиторий известен. Пилоты случайны, их ID API не возвращает; использовать математическое ожидание. Все пилоты первой версии берутся из полной однородной ячейки N. Для действия j с одинаковыми target и каналом вероятность хотя бы одного контакта конкретного человека:

```text
q_j = 1 − Π_pilots_of_j (1 − actual_n/N)
```

Для фиксированного набора истинных ratio, отсортированных от большего к меньшему, ожидаемый лучший эффект:

```text
B(actions) = Σ_j ratio_j × q_j × Π_(k<j)(1−q_k)
```

Если контактов нет, вклад 0. Отрицательные ratio входят в сумму; фиктивный бесплатный вариант 0 в max не добавляется. Для финального подмножества добавить его действие с q=1, вне его оставить только пилоты. Умножить B на baseline-суммы соответствующих частей. Повторные одинаковые действия можно объединить по q; независимость относится к отдельным случайным выборкам, не к клиентам внутри одной выборки. Формула проверена полным перебором 36 сочетаний двух пилотов.

**Дополнительный публичный агрегат:** при ненулевом конечном y из ответа можно получить `A_sample=observed_lift_total/y`. Это сумма baseline пилотной выборки, а не её ID; тождество отдельно проверено. Сохранять её в журнале при численно корректном делении. Формула q выше интегрирует случайный состав **без условия на A_sample**, поэтому использует не всю доступную информацию и остаётся приближением к прогнозу по полной истории. Отдельное улучшение: для единственного пилота в ячейке и финала на всю эту ячейку считать точно при заданных ratio `A_cell*r_final + A_sample*max(r_pilot−r_final,0)`. Для нескольких пилотов/частичного финала нужны оценки пересечений; нельзя просто заменить все q на доли ARPU и объявить результат точным. Реконструкция ID не требуется.

При разных target/каналах `max(средних)` отличается от `среднего max`. Поэтому рекомендуем оценивать все планы на **одних 64 выборках posterior**: при старте act с seed42 создать фиксированные стандартные нормальные `Z[draw,action]` по стабильному каталогу; после обновлений получать `θ=μ+√v Z`. Переиспользовать Z и для сравнения планов, и для проверки возмущений μ; из одного θ выводить все каналы. Разные target пока независимы — явное допущение. Для каждой выборки считать B, затем общий net:

```text
net_draw = gross_pilots_and_final − pilot_cost − final_cost
utility(P) = mean(net_draw) − k × std(net_draw)
```

Это уточнение синтеза по экономике Амира, §7 и портфелю Азамата, §2, **ещё не испытанное в полном агенте**. Оно учитывает неопределённость параметров, но интегрирует случайные пилотные ID по ожиданию: std не является полным разбросом реализованного счёта. Сравнить также простой plug-in вариант. Известные затраты пилотов вычитаются один раз; их постоянная часть отменяется при сравнении планов, однако эффект может меняться из-за финальных контактов.

## 6. Поиск конечного плана

1. Обычные кандидаты строить из пилотированных действий: целая ячейка и непустые допустимые data/call-фильтры. Все три канала, один target на ячейку; каналы подгрупп могут различаться. Непилотированные target не масштабировать только на prior. Fallback допускает непилотированное действие с явно широкой оценкой.
2. Проверять маски на пересечение: целая ячейка и её часть конфликтуют. Не исключать внутренне ID, которые финальный фильтр по-прежнему выбирает. При нехватке ресурса симулятор допускает реальный усечённый префикс.
3. Построить четыре старта: добавочный utility; utility на контакт; utility на `n/H + cost/B + 1/10`; SMS-старт с последующей заменой каналов. Здесь H/B — текущие остатки. Если B=0, оставить push и исключить денежный член. Сохранять только добавления, улучшающие один и тот же utility.
4. Выбрать лучший. Проверить замену target/канала, удаление/добавление строки, обмен 1↔1 и 1↔2 на сокращённом списке; перебрать соседние перестановки строк. После каждой попытки пересчитать **весь** план. Принимать строгое улучшение, например >1e−8; фиксированный лимит 2 000 попыток и дедлайн.
5. Совместимые from можно объединить через `;` при одинаковых остальных фильтрах, target и канале. Только после пересчёта маски, cap5000 и utility; это упаковка отдельных оценок, не новый смешанный пилот. В первой реализации объединение необязательно.
6. Валидировать 1–10 непустых кампаний и всю схему самостоятельно: экспортёр не повторяет `sanitize_campaigns`. Сохранять лучший найденный **непустой** план независимо от знака общего utility: уже понесённый ущерб пилотов не отменяет полезных добавлений. Одиночный fallback нужен, если поиск вернул пустой план: выбрать наибольший utility среди допустимых малых фильтруемых аудиторий и дешёвых каналов. Сравнивать его и с сохранёнными непустыми планами. Размер «100 человек» нельзя просто записать в финальную строку. Не обещать положительный net во всём отрицательном мире.

## 7. Контракты модулей, время, сбои

| Модуль будущего решения | Контракт |
|---|---|
| `candidates.py` | Каталог, ранги, маски, ID-префиксы; fallback без исторического файла |
| `beliefs.py` | `update(action, channel, actual_n, ratio)`, posterior и согласованные выборки каналов |
| `planner.py` | Точный расход ресурсов; ожидаемые пилотные пересечения; `plan(beliefs, ledger, resources)` |
| `agent.py` | `Agent.act(env)`: журнал, цикл пилотов, остановка, валидный финал |
| `report.py` | Локальное объяснение; опциональная LLM вне вычисления CSV |

Фиксировать RNG в начале **каждого act** (например, 42); стабильные сортировки и tie-break; не хранить знания от предыдущего env. Одинаковые posterior-выборки использовать для всех альтернатив в одной итерации. Изолировать отсутствующий артефакт и ожидаемые ошибки API; не ретраить бесконечно. После сбоя читать реальные остатки, использовать последний успешно проверенный план, повторно проверив его на новых ресурсах; не включать испорченный ответ в posterior.

Цель act — до60с, внутренний стоп исследования/поиска в210с, возврат до240с. Пока это цели, не замеры. Для воспроизводимости ограничивать работу также числом операций; аварийный выход по часам может дать иной CSV на другом оборудовании, поэтому в обычном seed42 прогоне таймаут не должен срабатывать. Никаких обязательных сетевых вызовов. Итоговый README должен различать прогноз агента, шумное наблюдение и фактический результат evaluator.
